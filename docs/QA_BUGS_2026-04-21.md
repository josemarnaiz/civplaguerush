## Executive summary

The run loop is currently unplayable end-to-end because of two P0 defects:

1. **BUG-001**: All three decision buttons render stacked on top of each other at the same layout position (only the last one is visible/clickable on screen).
2. **BUG-002**: A fresh run ends in `VICTORY` after only 3 decisions on Turn 1, with the HUD still showing `Control 2/7` and `Crisis 23`. The 24-turn loop is never actually exercised.

There is also a third P0 latent defect that will surface once BUG-002 is fixed:

3. **BUG-003**: `WorldSimulation.evaluate_outcome` emits `"win"/"loss"/"timeout"/"ongoing"` but `RunEndOverlay` keys its strings by `"victory"/"chapter_cleared"/"defeat"/"loss"/"timeout"/"ongoing"`. A legitimate win today would display `"RUN OVER"` with no subtitle.

## Bug list

### BUG-001 — Decision buttons render stacked in the same position

- **Priority:** P0 (blocker)
- **Area:** RunScene / UI
- **Reproduction:**
  1. Delete user saves (see top).
  2. Main Menu → `Start Run`.
  3. Observe any event (`Information Leak`, `Mass migration…`, `Cure trial…`, etc.).
- **Expected:** The three choice buttons stack vertically inside the `Choices` VBoxContainer and are all visible/clickable.
- **Observed:** `game_get_ui` reports the three `@Button@*` children of `Choices` all at `position=(158, 437)` with `size=(1042, 54)`. Visually only the last button in the list appears on screen; the other two are occluded underneath it. Clicking the visible area registers as a choice but the player cannot actually pick between the three options (input picks the topmost at that coordinate).
- **Evidence:**
  - `game_get_ui` for the `Choices` container (same run):
    - `@Button@10` "Open corridors into Cradle" → `position=(158, 437)`
    - `@Button@11` "Seal the border" → `position=(158, 437)`
    - `@Button@12` "Resettle into adjacent holdings" → `position=(158, 437)`
  - Screenshots show only the last label visible inside the `EventPanel`.
- **Root cause (hypothesis, already localized):** `scripts/run_scene.gd::_animate_event_reveal` (~lines 279-292) iterates the `choices_container` children and does:
  ```
  btn.position.y = 8.0
  ...
  ct.tween_property(btn, "position:y", 0.0, 0.30).set_delay(delay)
  ```
  Assigning `position.y` on a child of a `VBoxContainer` overrides the container's layout-assigned position. The tween then pins all buttons at `position.y == 0` (relative to the container), collapsing them to the same absolute `y`. The container's automatic vertical stacking is effectively disabled while the tween is alive.
- **Suggested resolution (not executed):**
  - Animate `modulate:a` only for the stagger. No positional animation.
  - Or wrap each button in a `MarginContainer`/`Control` that owns the animation offset, so the VBox still places each wrapper and only the wrapper's local offset is tweened.
  - Or capture the layout-resolved `y` for each button after `await get_tree().process_frame` and tween from `base_y + 8` → `base_y`.
- **Regression guard:** Add a headless test or an in-game `game_eval` check that verifies, after `_render_current_event`, no two children of `choices_container` share the same `global_position.y`.

### BUG-002 — Run ends with `VICTORY` on Turn 1 with `control_regions = 2/7`

- **Priority:** P0 (blocker)
- **Area:** RunScene / WorldSimulation
- **Reproduction:**
  1. Delete user saves.
  2. Main Menu → `Start Run` → resolve all 3 decisions of Turn 1 (click the visible button three times).
  3. Watch the `RunEndOverlay` appear with title `VICTORY` and subtitle "The coalition holds. The Ash remembers you.".
- **Expected:** After Turn 1, `evaluate_outcome` returns `"ongoing"` (neither win nor loss nor final turn) and `_start_turn()` is called to advance to Turn 2.
- **Observed:** `_finish_run` is reached and the overlay is shown. HUD prior to the overlay: `Turn 1/24 · Decision 3/3 · Stab 47 · Inf 45 · Res 25 · Crisis 23 · Control 2/7`. Overlay then shows `VICTORY / The coalition holds. The Ash remembers you.`.
- **Config context (from `data/run_config.json`):**
  - `target_control_regions = 7`, `max_crisis_for_win = 50`
  - Starting state: `stability 60, influence 45, resources 35, crisis 25, control_regions 2`
  - Starting regions with `influence >= 60` (control threshold): `r01 N.Arc (70)`, `r02 Coast (60)` — 2 regions. Matches the displayed `2/7`.
- **Evidence of real win decision:** `user://last_run_result.json` (pre-existing, not written by today's session) shows a legit past win with `control_regions=9 crisis=52 turn=15`. Today's session did not overwrite this file (timestamp still 2026-04-20 16:36) even though the overlay clearly rendered with the `"victory"`/`"chapter_cleared"` subtitle — which is itself a red flag; see hypotheses.
- **Hypotheses to validate (root cause not confirmed):**
  1. HUD vs. real `world_state` desync: `_render_state()` is called at the end of `_render_current_event`, but `_finalize_turn` applies passive effects and advances the turn without calling `_render_state()` again before `evaluate_outcome`. If `apply_effects` for a `control_regions:+N` choice calls `region_grid.distribute_effect("boost_lowest_influence", 15, "influence", N)` on multiple regions, HUD shows stale control count while the real `world_state["control_regions"]` may jump past 7.
  2. Player-chooses leak on `cure_trial`: while `_awaiting_region_pick` is true, the 3 choice buttons are disabled but still present at the same stacked position (BUG-001). An input that hits the stack while disabled may propagate unexpectedly, or the stack's disabled state might not block `pressed` on all of them.
  3. Recursion into `_finalize_turn` via `_render_current_event` when `current_turn_events.is_empty()` after `event_director.next_choices` returns fewer events than requested.
  4. `show_outcome` being invoked with a value that lowercases to `"victory"` or `"chapter_cleared"` from a path we have not yet located. The evidence for this is that the overlay actually rendered `"VICTORY"` + the full subtitle — yet `evaluate_outcome` only emits `"win"`. If the overlay truly received `"win"` the title would be `"RUN OVER"` and the subtitle empty (see BUG-003). So either (a) the overlay is being fed `"victory"` from somewhere else, or (b) the overlay we saw was not triggered by the normal code path. This hypothesis is the highest priority to verify because it points at a second unknown caller.
- **Suggested investigation steps (not executed):**
  - Add `push_warning` logs inside `_finalize_turn` printing `turn_index`, full `world_state`, `is_win`, `is_loss`, `is_final_turn`, and the outcome string.
  - Add `push_warning` in `RunEndOverlay.show_outcome` logging the received outcome and caller stack (via `get_stack()` while running in debug).
  - Grep for any non-obvious calls that could set `RunEndOverlay` text directly (none found in current search — confirm there isn't a test hook wired by the autoload `McpInteractionServer`).
- **Suggested resolution (after root cause is confirmed):**
  - If it's HUD desync: call `_render_state()` at the start of `_finalize_turn` and again after `apply_passive_turn_effects` so the overlay can't claim a state the HUD never displayed.
  - Add a hard guard in `evaluate_outcome`: when `is_win` is true, assert `region_grid.controlled_count() >= target_control_regions`; `push_error` otherwise.
- **Regression guard:** Deterministic unit test: initialize `WorldSimulation` with the real `run_config.json` and a fixed state `{stability:47, influence:45, resources:25, crisis:23, control_regions:2}`, assert `evaluate_outcome()["outcome"] == "ongoing"`.

### BUG-003 — Outcome string mismatch between simulation and overlay

- **Priority:** P0 (latent; will surface as soon as BUG-002 is fixed)
- **Area:** RunScene / RunEndOverlay
- **Evidence:**
  - `scripts/systems/world_simulation.gd::evaluate_outcome` returns `"win" | "loss" | "timeout" | "ongoing"`.
  - `scripts/ui/run_end_overlay.gd` dictionaries are keyed by `"victory" | "chapter_cleared" | "defeat" | "loss" | "timeout" | "ongoing"`.
  - Only `"loss"`, `"timeout"`, `"ongoing"` overlap.
  - `scripts/run_scene.gd::_finish_run` passes the raw outcome string into `run_end_overlay.show_outcome(outcome)` with no translation.
- **Observed consequence:**
  - `"win"` → `TITLE_BY_OUTCOME.get("win", "RUN OVER")` returns `"RUN OVER"`, subtitle falls back to `""`, advisor falls back to arcanist.
  - The chapter-cleared beat (chancellor + "The coalition holds. The Ash remembers you.") is unreachable through the normal code path.
- **Suggested resolution (not executed):**
  - In `_finish_run`, translate outcome before passing to the overlay:
    - `"win" && chapter_goal_completed` → `"chapter_cleared"`
    - `"win" && !chapter_goal_completed` → `"victory"`
    - `"loss"` → `"defeat"` (optional; `"loss"` is already wired)
    - Other values pass through unchanged.
  - Or add alias keys to the overlay dictionaries (`"win" = "VICTORY"` etc.) and keep the chapter-cleared variant as a separate call path.
- **Regression guard:** Test that `RunEndOverlay.show_outcome` never has to fall back to `"RUN OVER"` for outcomes produced by `WorldSimulation.evaluate_outcome` in normal runs.

### BUG-004 — Inconsistent default fallback values for win conditions

- **Priority:** P1
- **Area:** Data / Simulation defaults
- **Evidence:**
  - `data/run_config.json`: `target_control_regions: 7`, `max_crisis_for_win: 50`.
  - `scripts/systems/world_simulation.gd:143-144`: fallback defaults `8` and `60` when keys are missing.
  - `scripts/run_scene.gd:149`: fallback default `7` for the HUD target label.
- **Impact:** Today the JSON always provides these keys so this is latent. It becomes a real defect when a new chapter/profile or a hand-edited config omits a key — the HUD and the simulation will disagree silently (HUD says "7" while sim allows win at 8, or vice versa).
- **Suggested resolution (not executed):**
  - Extract defaults into one place (e.g., a `RunBalance` helper class or constants in `WorldSimulation`), reused by both `run_scene.gd` and `world_simulation.gd`.
  - Or assert required keys at `WorldSimulation.initialize` and fail loudly if absent.

### BUG-005 — `cure_trial` / `player_chooses` UX is unreadable

- **Priority:** P1
- **Area:** RunScene / RegionMap
- **Reproduction:** Any turn that rolls `cure_trial` or `relief_mission` (both are `template: "player_chooses"`).
- **Observed:**
  - Event description ends with an injected line `"> Pick an infected region to host the cure trial."`.
  - All 3 choice buttons are rendered but `disabled = _awaiting_region_pick`, so they appear greyed out.
  - Choice labels contain `"{region.short}"` which is rewritten to `"the region"` by `_display_text` until a region is picked — resulting in copy like `"Cautious limited trial in the region"`.
  - There is no prominent visual cue on the choices panel explaining that the map is the next input surface. The only hint is the `>` line tacked onto the description.
- **Impact:** Readable as "the UI is broken" rather than "the UI is waiting for a region pick". Strong bounce risk for new players.
- **Suggested resolution (not executed):**
  - Add a bold hint label inside the `Choices` container while `_awaiting_region_pick` is true: e.g., `"Select a region on the map above."` with the chapter gold color (O4).
  - Ensure `region_map.set_selectable(candidates)` produces a visible, animated highlight on valid regions (pulse/border). If the method already exists (see `scripts/ui/region_map.gd`), verify it is called and that the visual is noticeable.
  - Optionally hide the disabled choice buttons entirely during region-pick mode and swap them in only once a region is selected.

### BUG-006 — HUD shows stale state under the end-of-run overlay

- **Priority:** P2
- **Area:** RunScene
- **Evidence:** Right before the overlay appears, the HUD still shows the pre-finalize state (`Turn 1/24 · Control 2/7` in our repro). Passive effects and `advance_turn()` already ran behind the scenes.
- **Impact:** Reinforces BUG-002 confusion and, even after BUG-002 is fixed, makes legitimate victories look inconsistent with the displayed numbers.
- **Suggested resolution (not executed):** Call `_render_state()` at the top of `_finalize_turn` after `apply_passive_turn_effects` and `advance_turn()`, before `evaluate_outcome`, so the HUD reflects the state used for the decision.

### BUG-007 — `RunEndOverlay.tscn` ships with hardcoded `"VICTORY"` placeholder text

- **Priority:** P2
- **Area:** RunScene / RunEndOverlay
- **Evidence:** `scenes/RunEndOverlay.tscn` sets `Title.text = "VICTORY"` and `Subtitle.text = "The coalition holds."` at scene load. `run_end_overlay.gd::_ready` only sets `visible = false`; it does not clear the text.
- **Impact:**
  - If the overlay is ever drawn with non-zero alpha before `show_outcome` runs (layout hiccup, tool inspection, tween race), the player sees a misleading "VICTORY".
  - During debugging, `game_get_ui` reports a Title of `"VICTORY"` even before any run finishes, which is noise.
- **Suggested resolution (not executed):** Replace placeholder text with neutral strings (`"--"` / empty) in the `.tscn`, or clear them in `_ready()` before returning.

### BUG-008 — Map region labels `I:NN V:NN` lack a legend and disagree with tooltip wording

- **Priority:** P2
- **Area:** RegionMap UI
- **Evidence:**
  - On-map label format: e.g., `"Cradle I:10 V:70"`.
  - Tooltip on hover shows `"Influence N · Infection N · Stability N · Neighbors N"`.
  - `I` seems to map to `influence`, `V` to `infection`, but the letters are ambiguous (`V` = "viral"? "virulence"? not self-evident).
  - No visible legend on the map.
- **Impact:** Higher-than-necessary learning curve. Stability is shown in the tooltip but absent from the map label, making per-region stability invisible at a glance.
- **Suggested resolution (not executed):**
  - Unify abbreviations (e.g., `Inf:N Vir:N` or `INF/INC/STB`).
  - Add a small static legend in a corner of the map describing each abbreviation.
  - Consider showing stability on the label too, or surfacing it with a dedicated tint/icon.

### BUG-010 — Engine errors `button == MouseButton::NONE` on shutdown

- **Priority:** P3
- **Area:** QA tooling (MCP input injection)
- **Evidence:** On `stop_project`, the engine flushed five occurrences of `ERROR: Condition "button == MouseButton::NONE" is true. Returning: MouseButtonMask::NONE at: mouse_button_to_mask`.
- **Likely cause:** Synthetic `InputEventMouseButton` events from the MCP server omitting `button_index` (defaults to `MOUSE_BUTTON_NONE = 0`).
- **Impact:** QA-only noise; does not affect human play.
- **Suggested resolution (not executed):** In the MCP server, set `event.button_index = MOUSE_BUTTON_LEFT` explicitly when constructing click events.
